# Arcaea 7.0.260c 偏移证据

语言：[English](7.0.260c-offsets.md) | 简体中文

目标：`libcocos2dcpp.so`（ARM64，已剥符号）

- SHA-256：`09fad9e3299acf9b68613b8418c6dcc1bd7f200e42945198f369bbf491e9ad34`
- Build ID：`7c171c3dab4cf5b73dc2b1c3e7728fc0879f09cd`
- FMOD provider SHA-256：`7f67c6940afaeaad1c05857d118e4a1d223c0a625a593369c80358e7b02d1d8c`

全部 19 个被消费函数由 `scripts/port_match.py` 从 7.0.255c 迁移；spec 的
21 个目标里 20 个（含 songlist 资源打开函数）在第二次 locate 复跑中固定并
复核通过，记录在 `scripts/port_match_70260c_spec.json`。迁移后的
`ShowJudgementEffectAtNote` 保持 7.0.255c 的函数边界（0xAC8 字节）与
prologue。`registry_getter` 低于匹配器的投票下限，改用精确掩码字节固定；
IDA 另行确认了版本全局变量、直接调用关系、RTTI 对象、资源加载调用点、
曲目注册表全局变量与 scenecontrol getter。

## 语义确认

- `0x1922684` 的版本 setter 把 Java 字符串复制到 `0x1BE5F68` 的 libc++
  string（另有第二份副本写入 `0x1BEFCE0`），指令形态与 7.0.255c 的 setter
  完全一致，现有运行时识别模型可以直接沿用。
- `processLogicNotes` 从 `Gameplay +0xA0/+0xA8` 读取 note vector，以与
  7.0.255c 相同的 Tap/Flick/Long/Arc/Camera/SceneControl 分派逻辑遍历，调用
  `ScoreState_applyMiss @ 0x1727198` 与 `ScoreState_applyJudgement @
  0x156EBA8`，并经 `__dynamic_cast` 引用 `_ZTI12LogicArcNote @ 0x1ADC2C8`。
  miss 窗口的 timer 读取保持共享 Timer 镜像的
  `+0x20/+0x28/+0x2D/+0x34` 位移。
- `tryTapJudgementForTouch` 同时引用 Hold/Arc 两处 RTTI
  （`0x1B61FA8` / `0x1ADC2C8`），并在 note `+0xA8` 写入 hold 头部激活标志；
  ELF 相对重定位把唯一类型名 `"13LogicHoldNote" @ 0x4E058C`、
  `"12LogicArcNote" @ 0x43FC8B` 分别绑定到这两个 `_ZTI` 对象。
- `ShowJudgementEffectAtNote` 保持 7.0.255c 的边界（0xAC8 字节）与
  prologue；与 7.0.255c 的掩码 diff 原样率 83.2%，且两个调用者恰好仍是
  `note_effect_on_miss +0x11C` 与 `note_effect_on_judgement +0xB8`
  ——与 7.0.255c 的调用点完全相同。
- `HttpClient_processRequest` 仍保持 7.0.255c 的请求类型分派
  （`request+0x0C`，经 `response+0x10` 取得）、`+0x28/+0x30` 的 body
  范围，并调用迁移后的 `0xE1D294` curl wrapper。
- 小 getter（`sub_165C7A8`，0x20 字节）读取 `0x1BE0DD0` 的全局变量并解引用
  `+120`、`+24`——与 7.0.255c 对 `qword_1BE7028` 的链路完全一致，确立了调用
  `find_song_by_id` 前使用的曲目注册表 owner 全局变量；迁移后的
  `find_song_by_id` 仍在 `arg+24` 做同样的 map 查找。0x20 字节的函数体无法
  参与投票，locate 通过 expect_bytes 固定该函数。
- scenecontrol getter 仍是全二进制唯一的 8 字节
  `LDRB W0,[X0,#0x110]; RET`，位于 `0x83DDAC`。
- songlist 资源打开函数是迁移后的 cocos2d-x `FileUtilsAndroid` asset
  路径：`AAssetManager_open` PLT stub（`0x1A624D0`）恰好只有两个调用者，
  songlist 侧调用位于函数 `+0x200`（`0x165A200`），调用点模式
  `BL; MOV X20,X0; CBZ X0` 逐字一致，并带有 `CCFileUtils-android.cpp`
  字符串。其函数边界回到 7.0.1c 形态的 `0x418` 字节（7.0.255c 曾把额外的
  辅助逻辑内联成 0x744 字节函数体）；这也是首轮 locate 把一个多人教程
  相似函数排在前面的原因，已通过 PLT 调用者检查裁决。
- 成对比较 gameplay、play launcher、chart path 与 availability 函数后，
  所有被消费的对象位移均保持不变。因此 7.0.260c 复用 7.0.x note 派生布局
  （`isVoid +0xA4`、`activeNow +0xD0`、运行时 X/Y
  `+0xD4/+0xD8`、hold head `+0xA8`）以及未变的自定义谱面 Song 布局
  （`remote_pack +0x1C0`、难度表 `+0x228`、lock `+0xF0`）。
- `libfmodProvider.so` 仍在 `0x36AC8` 导出大小为 `0x3A0` 的
  `_ZN24AudioProviderFMODAndroid7loadBGMEPKci`。

## 复现命令

```bash
python scripts/port_match.py locate ../7.0.255c/libcocos2dcpp.so \
  ../7.0.260c/libcocos2dcpp.so scripts/port_match_70260c_spec.json
python scripts/port_match.py diff ../7.0.255c/libcocos2dcpp.so \
  ../7.0.260c/libcocos2dcpp.so scripts/port_match_70260c_spec.json
python tests/verify_profile.py 7.0.260c
python tests/run_host_tests.py
./build.ps1 --rebuild --rel
```

`tests/verify_profile.py` 固定校验精确 SHA-256、全部 Hook prologue、songlist
调用点、两个摘要守卫、scenecontrol getter 与全部运行时补丁原值。
